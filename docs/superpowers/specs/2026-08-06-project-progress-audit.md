# Project Progress Audit

Audit date: 2026-08-06  
Source: local repository files only  
Status: current working tree is dirty and not committed

## Verification Run

- `bun test` passed: 76 tests, 0 failures, 15 files.
- `bun run lint` passed: TypeScript check and ESLint completed.
- `bun run build` passed with Vite 8.1.4.
- Build still prints the Vite warning that `vite-tsconfig-paths` can be replaced with native `resolve.tsconfigPaths`.
- Live database migration was not verified in this audit. Existing migrations are present, but `bun run db:migrate` was not rerun against Postgres.

## Foundation And Tooling

- The app is now a TanStack Start, React 19, TypeScript 7, Vite 8 project.
- Development server is configured for `localhost:3000` with `strictPort`.
- Drizzle is configured for PostgreSQL in `drizzle.config.ts`.
- Local Postgres support exists in `docker-compose.yml` using an Alpine Postgres image.
- Environment examples exist in `.env.example`; real values are kept in `.env`.
- `AGENTS.md` exists with contributor guidance for this repository.

## Routing Structure

- Routes were reorganized into readable TanStack file-route folders, closer to Next.js style.
- Public routes include login, online application, and website pages.
- Authenticated routes cover dashboard, admission, school, madrassa, students, finance, reports, settings, parents, teachers, HR, notifications, inventory, and ID cards.
- API routes now live under `src/routes/api/` and cover auth, setup, admissions, students, academic setup, academic years, attendance, fees, exams, teachers, parents, and notifications.

## Auth And User Management

- Better Auth is integrated with the Drizzle PostgreSQL adapter.
- Email/password sign-up is disabled for normal public self-registration.
- Better Auth plugins are configured for username login, admin support, and TanStack Start cookies.
- Roles include super admin, admin, principal, HR manager, accountant, librarian, receptionist, teacher, staff, and parent.
- The database schema enforces only one `super_admin` user with a partial unique index.
- Super admin bootstrap, recovery, and current-super-admin update APIs exist.
- User management still exists, but some UI remains mixed Urdu/English.

## Parent Login And Portal

- Parent login is implemented with username plus password.
- Staff login uses email plus password.
- The login page has mode switching for staff and parents and is mostly Urdu.
- Parent usernames are generated from the guardian name plus random digits; no sequence table is required.
- Better Auth still receives an internal hidden email for technical compatibility, but parents see and use the username.
- Parent account creation happens during accepted/direct admission when requested by the admission flow.
- Parent account creation is fail-safe: admission succeeds even if account creation fails, and the student event log records the failure.
- A parent portal exists at `/parents` with linked students, fees, attendance, exam results, events, and local notifications.

## Academic Structure

- Current seeded top-level institutions are:
  - Al-Qasim Academy as a formal school.
  - Jamia Qasmia Baneen as the boys madrassa.
  - Jamia Zainab Banat as the girls madrassa.
- Jamia Zainab school support exists as an informal nested program, not a separate top-level school.
- Programs exist for school, Hifz, Nazira, Dars-e-Nizami, and school support.
- Madrassa grade catalogs were added from the provided boys/girls grade breakdown image.
- Boys and girls madrassa grades are separated and include preparatory, Nazira, Hifz, Dars-e-Nizami, Tajweed, Takhassus, and short-course style entries.

## Academic Years And Promotions

- Academic years are stored separately for school and madrassa systems.
- School academic years use Gregorian dates.
- Madrassa academic years use Hijri year labels with confirmed Gregorian start/end dates.
- The settings UI includes academic-year creation, activation, lock/archive behavior, and rollover controls.
- Promotion rules and promotion runs exist for yearly carry-forward between classes, sections, darja, or programs.

## Admissions

- Admission backend integration exists for school and madrassa variants.
- Admission variants include school boys/girls, boys Nazira, boys Hifz, boys general madrassa, girls general madrassa, and girls Nazira.
- Direct admission and application review/accept/reject flows exist.
- Admission acceptance creates the student, enrollment, student event log entries, guardian links, sibling links when provided, and optionally parent login credentials.
- Admission requires an active academic year for the correct system: school or madrassa.
- Admission reference numbers, admission numbers, and roll numbers are generated by backend numbering logic.
- The form number is generated and displayed by the system; it should not be manually typed.
- Sample-data fill support exists for large admission forms and respects gender-specific forms.
- Admission print work includes template-backed forms and typed Urdu output references from files in `public/`.
- Boys and girls Auhad Nama PDFs are present in `public/`.

## Students, Guardians, Siblings, And Timeline

- Student registry is backend-backed.
- Student profiles have personal, academic, guardian, sibling, and activity views.
- Direct student creation was removed as the main workflow; admissions are the intended source of truth.
- Enrollment movement exists through `/api/students/:id/enrollments/move` and UI dialogs.
- Guardian management can link guardians, set primary guardian, and retry parent account creation.
- Sibling management exists.
- Student timeline is implemented with event categories for admission, academic movement, guardians, siblings, account events, status, attendance, finance, and exams.
- One known issue was fixed around student profile loading where guardian columns were referenced without the correct join.

## Attendance

- Attendance V1 exists for school and madrassa rosters.
- Teachers can mark student attendance only for their assigned classes, sections, darja, or placements.
- Attendance reports include daily summaries and student history.
- Attendance calculation tests exist.

## Fees And Finance

- Fees V1 exists with on-demand charges instead of automatic monthly generation.
- Payment collection, partial payment allocation, opening balance, student ledgers, and outstanding reports exist.
- Finance reports include daily collection, outstanding balances, student ledger, institution summary, and reversal/refund audit.
- Reversal and refund workflows exist for charges and payments.
- Finance domain tests exist.

## Exams

- Seating-plan work was based on `public/exam-seating.html`.
- Seating generation, result calculation, DMC, and transcript server functions exist.
- Exam calculation and seating tests exist.

## Teachers

- Teacher access control is connected to attendance marking for assigned placements.
- A separate Add Teacher flow currently exists.

## Notifications

- Student events can generate local notifications.
- Parent notification views and read tracking exist.

## Frontend And UX
