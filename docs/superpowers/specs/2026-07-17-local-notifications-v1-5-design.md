# Local Notifications V1.5 Design

## Scope

Local Notifications V1.5 turns the existing in-app notification event log into a local communication module. It does not integrate SMS, WhatsApp, email, push notifications, or any third-party provider. All notifications stay inside PostgreSQL and the authenticated app UI.

Included:

- Local in-app notices for parents and staff.
- Admin-created announcements.
- Optional scheduled publishing and expiry.
- Read/unread tracking per user.
- Filters by category, read state, audience, and source.
- TanStack Query key factories for parent and notification cache consistency.

Not included:

- SMS, WhatsApp, email, push, payment links, provider delivery queues, or provider response logs.
- Parent chat or two-way messaging.
- Anonymous/public notice access.

## Architecture

Keep `notification_events` as the single source for both automatic system events and manual announcements. Normalize the server/domain vocabulary around local statuses:

- `recorded`: automatic event generated by the system.
- `published`: visible local announcement/event.
- `scheduled`: not visible until `publishAt`.
- `archived`: hidden from normal notification lists.

Add optional `source`, `publishAt`, and `expiresAt` fields. `source` distinguishes system-created events from manual announcements. `publishAt` and `expiresAt` control local visibility. No delivery channels beyond `in_app` are used.

## Data Flow

Automatic student events continue to create local parent/staff notification records. Admin-created announcements use a `POST /api/notifications` route. The service validates input with Zod, checks staff permissions, expands the chosen local audience to notification rows, and stores them as local events.

Parents read only their own guardian/user notifications. Staff can read staff notices and operational events through existing permission checks.

## TanStack Practices

Client code uses query key factories:

- `notificationKeys.list(filters)`
- `parentKeys.dashboard()`
- `parentKeys.guardianAccounts(filters)`

Mutations invalidate targeted keys instead of broad ad hoc arrays. API routes keep request parsing and response shaping thin, while business logic stays in `src/lib/server/...`.

## UI

The notification center remains dense and operational. Staff users get a compact “New Announcement” action that opens a dialog. Parents only see their received local notices and cannot create announcements.
